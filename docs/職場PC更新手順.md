# 職場の Windows PC で更新する手順

スマートフォンでは、GitHubで表示できる[短い更新・復旧手順](../UPDATE.md)も利用できます。

今回の更新は Node.js と Next.js などの更新です。PostgreSQL、データベースの構造、既存のデータは変更しません。更新するのはアプリのコンテナだけです。

**最初に [更新版の検証結果](更新版検証結果.md)を確認してください。Docker での最終検証が未完了の間は、本番での実行を保留します。**

## 更新前に用意するもの

- Docker Desktop が起動している、いつもの職場のサーバー PC。
- **現在の本番フォルダー**。コピーした別フォルダーから実行しないでください。
- 毎日 17:30 に USB へ保存している `D:\formalin_backup_dir\formalin_next_db_v2.dump`。直近 24 時間以内のファイルを使います。
- 更新版のソースが共有リポジトリへ反映されていること。この手順書を作成しただけでは、職場の PC や GitHub は更新されません。
- イメージ取得・ビルド中のインターネット接続と、旧イメージの保存に十分なディスク空き容量。

作業は利用者へ知らせて、記録を入力していない時間帯に行います。ビルド中は旧アプリが動き続け、最後のコンテナ切り替え時に短い停止が発生します。`.env` と `.env.docker` は現在の設定を維持してください。

17:30 の自動バックアップが終わってから作業してください。17:30 をまたぐ作業や、バックアップ実行中の更新は避け、途中で USB を抜かないでください。

## 更新する

1. 職場のサーバー PC で、**いつも `git pull` している本番フォルダー**を VS Code で開きます。「ターミナル」→「新しいターミナル」で PowerShell を開き、次を実行します。

   ```powershell
   Get-Location
   Test-Path .\docker-compose.yml
   git status --short
   ```

   パスがいつもの本番フォルダーで、`Test-Path` が `True`、`git status --short` が空なら進めます。変更が表示された場合は、その場で止めて確認します。`git reset --hard` で消さないでください。

2. USB バックアップの取得結果を確認します。

   ```powershell
   Get-Content 'D:\formalin_backup_dir\backup_log.txt' -Tail 1
   Get-Item 'D:\formalin_backup_dir\formalin_next_db_v2.dump' | Select-Object Length,LastWriteTime
   ```

   ログの末尾が `exit=0`、`size=0` 以外であることを確認します。ファイルの `Length` がログの `size` と一致し、`LastWriteTime` が直近のバックアップ時刻であることも確認します。USB が見つからない、`exit` が 0 以外、サイズが 0、または 24 時間以上前なら、更新へ進まないでください。

3. 更新版を取得します。失敗したら、その場で止めます。

   ```powershell
   git pull --ff-only
   if ($LASTEXITCODE -ne 0) { throw '更新版の取得に失敗しました。ここで停止します。' }
   ```

4. 更新します。USB の保存先はスクリプトに設定済みなので、そのまま実行できます。

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\update-production.ps1
   ```

   スクリプトはファイルの存在・サイズ・更新日時・カスタム形式のヘッダーを確認し、ログがあれば成功とサイズも照合します。USB のダンプを PC 内へコピーし、読み取り専用で `pg_restore --list` に渡して、Formalin・History・User の表が含まれることを確認します。**内容一覧の検査であり、完全な復元テストではありません。** 検査で止まったら、エラーを確認してから対処してください。

スクリプトは現在の本番コンテナと DB の所属・保存先を照合し、旧アプリのイメージと切り戻し情報を `.deployment-backups\日時\` に保存します。その後、アプリだけをビルドして切り替え、Node.js / Next.js のバージョン、ログイン画面の HTTP 応答、DB コンテナ・保存ボリュームが同一であることを確認します。ビルドに失敗した段階では、旧アプリを停止しません。

完了時に表示される `Rollback state: ...\state.json` のパスを控えてください。`.deployment-backups` には旧イメージなどの機密情報を含む可能性があるため、公開・共有せず、動作確認が済むまで保持します。

成功の目印は `Update complete: Node.js 22.23.4; Next.js 15.5.28; login page HTTP 200.` です。通常の Compose が使うイメージの参照も新しい版へ揃えます。エラーが出た状態で、従来の `docker compose up` や再ビルドを追加実行しないでください。

## 更新後にブラウザーで確認する

- サーバー PC と、普段利用する職場内の別 PC の両方からアクセスできる。
- いつものアカウントでログインできる。
- 既存のホルマリン一覧・在庫・履歴が表示され、更新前の記録が残っている。
- 通常の業務操作を 1 件行い、一覧・在庫・履歴への反映を確認する。

ログイン画面の表示確認だけでは、認証やデータの読み書きまで確認できません。上記の確認を終えてから、利用者へ作業完了を知らせます。

## 不具合があったらアプリを戻す

同じ本番フォルダーのターミナルで、次の1行を実行します。直近の更新作業の保存状態を自動で選ぶため、日時の入力は不要です。直近の作業がビルドだけで失敗していた場合は、元のアプリが動いていることを確認して保持し、それより前の更新を勝手に取り消すことはありません。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\rollback-production.ps1
```

保存した旧アプリのイメージを読み込み、**アプリだけ**を元へ戻します。DB は復元せず、更新後に入力された業務データも維持します。ソースファイルは更新版のままなので、原因を直すまでは再ビルドしないでください。切り戻し後もログイン・在庫・履歴を確認します。

旧イメージがPC内に残っている場合は再利用し、アーカイブの読み込みを省きます。特定の保存状態へ戻す必要がある場合は、更新時に表示された `state.json` を `-StateFile '実際のパス'` で明示できます。

この更新・切り戻しでは、`docker compose down -v`、ボリューム削除、DB の初期化、Prisma のマイグレーションを実行する必要はありません。

## バックアップの復元確認について

教えていただいた自動実行スクリプトは、PostgreSQL 17 コンテナから `pg_dump -F c` でカスタム形式のダンプを取り、`cmd /c` のリダイレクトで USB へ書いています。この形式と書き出し方法は、そのまま活かします。既存の自動バックアップスクリプトやスケジュールは今回変更していません。

同じファイル名へ毎日上書きする運用なので、更新スクリプトは選んだダンプを `.deployment-backups\日時\database-before.dump` にコピーして保持します。本番へ試しに復元することはありません。実際の USB ダンプを別の検証用 DB へ復元できることは、既存のバックアップ運用の中でも確認してください。
